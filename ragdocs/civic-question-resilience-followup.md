## 4. New Risks / Regressions Introduced by Fixes

### 4.1 National scope over-triggering (P1-8 regression) — **High**

- **Evidence:** `is_national_scope_question` `app/filters.py:680` marker `"national"` alone matches any query containing word `national`. `contains_phrase` `app/filters.py:659-663` is word-boundary safe (`" national "` in `" national assembly promises "`), so `National Assembly` queries hit. `mentions_region` guard `app/filters.py:694-697` only checks `KNOWN_REGIONS` — NASS queries have no region, so guard does not fire. Pipeline `app/pipeline.py:158-166` then clears `meter_name` and `promise_tracker_name` when `national_scope=True`, stripping the NASS filter.

- **Failing example:** `List promises of the National Assembly` → `is_national_scope_question=True` → `filters` loses `promise_tracker_name=Legislative Tracker` → `_balance_national_records` `app/pipeline.py:304-331` searches `NATIONAL_METERS` (`batometer`, `senate`, `hor`) `app/filters.py:463-467` instead of legislative tracker scope. Similarly `national health promises` would incorrectly become national-balanced.

- **Mitigation considered:** The original audit's P1-8 suggested adding `national`/`federal` without noting the collision with `National Assembly`/`Federal Government` as entity names. A safer marker set would be phrases like `across nigeria`, `nationwide`, `whole country`, `for all nigerians` (already present) plus `nationally`/`federal government` as phrases, not `national`/`federal` as standalone words. Alternatively, `is_national_scope_question` should exclude queries where `infer_filters` finds `promise_tracker_name`/`meter_name` indicating a collection is explicitly named.

### 4.2 Anaphora over-triggering — `him`/`her`/`his`/`same` (P0-3a) — **Medium**

- **Evidence:** `needs_conversation_context` `app/query_rewriter.py:97-99` now includes `him`, `her`, `his` plus bare `same` `app/query_rewriter.py:85`. `contains_phrase` `app/filters.py:659` is word-boundary safe, so `him` inside `himself` does NOT trigger — verified: normalized `"himself"` does not contain `" him "`. However bare `same` triggers on `same state`, `same governor`, etc., and also on incidental `same` in civic sentences like `What is the same promise as before?` — intended. Risk is broader: `Tell me about him` after a governor answer correctly triggers rewrite, but `What did he say about education?` contains `he` not `him` — not triggered (only `him`/`his`, not `he`). More importantly, `him`/`her` are common English words; any query with them now forces LLM rewrite `app/query_rewriter.py:39-60` when history exists, even if `him` refers to a promise description, not conversation anaphora.

- **Impact:** Unnecessary rewrite calls add latency + LLM cost and may distort standalone queries. `validate_rewrite` `app/conversation.py:83-103` guards only length/growth/control chars, not semantic drift. No semantic validation as noted in original audit §4.3.

- **Example false trigger:** Standalone `Tell me about his achievements` (without history) correctly returns `RewriteValidation(True, source)` without LLM `app/query_rewriter.py:48` because `needs_conversation_context` returns true but `history` empty → early return. With history present (e.g., prior greeting), it would rewrite even though `his` is generic. Mitigation: require history length + pronoun proximity heuristics, or restrict `him`/`her` to `needs_conversation_context` only when `conversation_enabled` and history >0 (already gated `app/query_rewriter.py:47`).

### 4.3 Fuzzy topic false positives (P1-7) — **Medium**

- **Evidence:** `_fuzzy_trigger_match` `app/filters.py:592-607` with `difflib ≥0.85` `app/filters.py:603` and `_one_edit_away` `app/filters.py:606` for tokens ≥4 chars, trigger ≥5 chars, len diff ≤2. Threshold 0.85 is the same as `app/pipeline.py:662` `_fuzzy_token_match` for lexical gate, but topic triggers are shorter. Example: `education` (9) vs `educaton` (typo, 8) diff 0.94 → correct. But `healthy` (7) vs `health` (6) ratio 0.92 → false positive health trigger for `healthy economy` query (which should be jobs/economy, not health). Verified: no `stopwords` exclusion for topics unlike `app/pipeline.py:634` which excludes display words. `infer_topic_space` `app/filters.py:580` iterates `TOPIC_SPACES` in dict order; health appears before jobs, so `healthy` query would get `topic_label=health` incorrectly, then `expand_question_for_retrieval` `app/filters.py:863-870` appends health terms to retrieval, polluting results.

- **No existing tests:** No typo or fuzzy eval slice in `evals/adjudication_cases.json` (8 slices ×15 only, no `typo` slice). Design does not yet include fuzzy cases.

### 4.4 Greeting/courtesy signal broadening — prefix stripping interaction — **Low**

- **Evidence:** `_COURTESY_PREFIX_RE` `app/prompt.py:370-379` now strips `abeg`, `how far`, `wetin`, `sannu`, `bawo ni`, `good day` `app/prompt.py:373-375`; iterates 3× `app/prompt.py:386` plus strips leading `and` `app/prompt.py:392`. `contains_courtesy_signal` `app/prompt.py:359-367` now also checks prefix and greeting pattern.

- **Positive:** `Abeg show me broken promises for Lagos` now correctly strips `Abeg` → `show me...` (verified via manual regex: `Abeg ` → `show me...`). `Good day, what is Tinubu promise on electricity?` → `what is Tinubu...` (verified).

- **Risk:** `How far, wetin you fit tell me about Tinubu light promises?` — first strip removes `How far,` → `wetin you fit...`; second iteration removes `wetin` → `you fit tell me...` — loses `wetin` which is Pidgin for `what` but not needed for retrieval (keywords `Tinubu`, `light` remain, so topic `electricity` `app/filters.py:98` still fires). Low harm. For `How far is the Lagos road promise?`, `is_greeting` `app/prompt.py:326` uses `fullmatch` `app/prompt.py:327`, so query not treated as greeting — correct (verified `How far is the road promise?` → `False`). No regression.

### 4.5 `okpebholo` dual mapping — collection member vs meter (P0-2) — **Low**

- **Evidence:** `KNOWN_COLLECTION_MEMBERS` `app/filters.py:402` maps `okpebholo` → `okpebholometer` (meter name, not member), while `KNOWN_METERS` `app/filters.py:354` maps `okpebholo` → `okpebholometer` as well. `infer_filters` `app/filters.py:509-515` picks `collection_member` via `KNOWN_COLLECTION_MEMBERS` iteration order — may get meter name instead of member for `Monday Okpebholo`. `app/pipeline.py:527-528` `if collection_member` then sets `promise_tracker_name=State Tracker`. `app/taxonomy.py:38` `okpebholometer` is also `BRANDED_METERS` `app/taxonomy.py:34-38`. Dual path is intentional per task (`monday okpebholo` as member vs `okpebholo` as meter fallback) but creates ambiguity: `List promises for Okpebholo` could be interpreted as meter vs member depending on `contains_phrase` order. Existing `app/taxonomy.py:101-112` normalization treats `okpebholometer` as branded meter, not Promise Ring — so queries may flip between meter and member buckets. Not a regression from before (same pattern existed for other governors), but worth noting as fragility if `meter_name` vs `collection_member` filter drives different DB constraints.
